PERSONAL PROJECT | ROBOTICS & CYBERSECURITY

SecuredRobotArmCar

Exploring robotics, embedded systems, and cybersecurity through a mobile robotic vehicle equipped with a robotic arm.

Project Overview

SecuredRobotArmCar is a personal project combining a mobile robotic platform with a robotic arm. The project explores how software, hardware, and communication systems interact to control a physical device.

The project also explores the importance of cybersecurity in connected robotics. When software is responsible for controlling physical hardware, protecting communication and control interfaces becomes an important security consideration.

This project provides an opportunity to investigate cyber-physical systems, device communication, command handling, and security-focused system design.

Technical Overview

Robotic Vehicle

A mobile platform that supports physical movement and provides the foundation for the robotic system.

Robotic Arm

A robotic manipulator integrated with the vehicle for controlled physical movement and interaction with objects.

Embedded Systems

Exploring the relationship between electronic components, embedded control software, and physical hardware operations.

Cybersecurity

Studying how access control, command validation, and secure communication principles relate to connected robotic systems.

Project Objectives

  • Integrate a mobile robotic vehicle with a robotic arm.
  • Explore communication between software and hardware components.
  • Understand how control commands affect physical robotic movement.
  • Examine cybersecurity risks associated with connected devices.
  • Document the design, operation, and testing of the robotic system.

Cybersecurity Relevance

Robotics systems connect software instructions to physical operations. This creates security challenges because unauthorized or unexpected commands can affect real-world devices.

The following security principles are relevant to the design and evaluation of this project.

Security Considerations

  • Authentication: Verifying the identity of devices or users requesting control.
  • Access Control: Restricting robotic operations to authorized controllers.
  • Command Validation: Checking incoming control commands before executing them.
  • Communication Security: Considering how commands and data should be protected in transit.
  • System Reliability: Handling unexpected commands, communication failures, and potential system errors.

Specific implemented security mechanisms and verification results will be documented in the project implementation and testing sections.

Security Implementation

SecuredRobotArmCar uses an ESP32 microcontroller to host a web-based control interface for a four-wheel robotic vehicle with a 5DOF robotic arm.

The system uses a modular C++ architecture to separate robotic hardware functions from web request handling and security logic. This makes the project easier to maintain, debug, and extend.

Implemented Security Features

  • PIN Authentication: Requires a valid PIN before allowing access to protected robot controls.
  • Brute-Force Protection: Tracks failed authentication attempts and temporarily restricts further attempts.
  • Intrusion Detection System: Monitors unauthorized requests, invalid session tokens, and repeated suspicious activity.
  • DoS Mitigation: Uses request rate limiting to restrict repeated unauthorized requests to the robot's web server.
  • Automatic Session Locking: Locks the control interface after a period of inactivity.

Security Limitations

The project demonstrates several practical embedded security mechanisms. However, the FNV-1a-based session token mechanism is not a cryptographically secure authentication method. A production system would require stronger authentication and transport security.

Denial-of-Service (DoS) Mitigation Testing

Testing Objective

One of the primary security objectives of SecuredRobotArmCar was protecting its ESP32 web server from unauthorized access and excessive HTTP requests.

Because the ESP32 operates with limited processing power and memory, excessive network requests could interfere with normal robotic operation.

I created a Python script called dos_attack.py to evaluate how the server responds to repeated unauthorized movement requests.

Testing Methodology

The Python script sends 12 rapid HTTP requests to the robot's movement endpoint without providing a valid authentication session token.

The purpose is to verify that unauthorized commands are rejected and that repeated failures trigger the server's intrusion detection and rate-limiting mechanisms.

Documented Example Output

The following is an abbreviated, formatted representation of the example output documented in my GitHub repository. 

[+] Target: http://[ROBOT_IP]/move?dir=forward
        [+] Sending 12 rapid unauthenticated requests...
            
        [1] HTTP 403 - Unauthorized request blocked
        [2] HTTP 403 - Unauthorized request blocked
        ...
        [6] HTTP 429 - Client rate limited
        [7] HTTP 429 - Client rate limited
            
        [+] Test complete

Understanding the Output

HTTP 403 - Forbidden: The web server rejected an unauthorized request. This indicates that the authentication checks prevented the request from proceeding normally.

HTTP 429 - Too Many Requests: After the configured threshold of unauthorized requests was exceeded, the server began limiting additional requests from the client.

Intrusion Detection: The IDS tracks unauthorized attempts, allowing the server to identify repeated failures and apply request restrictions.

Development Challenge

During development, I identified a request-handling issue where the robot's locked state could reject incoming requests before they reached the intrusion detection logic.

I addressed this by updating the request-processing flow so that suspicious requests are evaluated by the IDS even when the robot is already locked.

Results and Limitations

The documented test illustrates authentication enforcement and request throttling through HTTP 403 and 429 responses.

This is a targeted security test, not a comprehensive DoS resistance benchmark. Additional testing would be necessary to evaluate performance under sustained network traffic.
