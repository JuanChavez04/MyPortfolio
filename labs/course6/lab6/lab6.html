Lab 6 – Explore Signatures and Logs with Suricata

Course 6 - Sound the Alarm: Detection and Response

Overview

In this activity, I worked with Suricata, an open-source intrusion detection and network monitoring tool. I explored how Suricata processes network traffic, applies custom rules, and generates alerts in both fast.log and eve.json. This lab demonstrates my ability to write IDS rules, analyze alert logs, and interpret HTTP traffic captured from a packet capture file.

Scenario

As a security analyst, my task was to monitor network traffic using Suricata and trigger alerts based on a custom rule. I examined a packet capture file (sample.pcap) and analyzed Suricata’s output logs to understand how alerts are generated and what information they contain. This scenario reflects real-world IDS workflows where analysts must validate alerts, inspect logs, and confirm whether traffic matches expected patterns.

Custom Suricata Rule

I began by reviewing the custom rule provided in custom.rules. This rule triggers an alert whenever Suricata detects an HTTP GET request flowing from the internal network to an external destination. The rule is shown below: 

alert http $HOME_NET any -> $EXTERNAL_NET any 
(msg:"GET on wire"; flow:established,to_server; 
content:"GET"; http_method; sid:12345; rev:3;)

Analyzing fast.log Output

The fast.log file contains a simplified alert summary. Each alert includes the timestamp, rule signature, priority, protocol, and source/destination IP addresses. The alerts confirm that Suricata detected multiple HTTP GET requests from the internal host to Google servers.

Analyzing eve.json Output

The eve.json file provides detailed JSON-formatted alert data. This includes HTTP metadata such as hostname, URL, user agent, HTTP status code, and redirect information. These details help analysts understand the full context of the network activity.

Using jq to Parse JSON Logs

I used the jq tool to extract specific fields from eve.json, such as timestamps, flow IDs, signatures, protocols, and destination IPs. This is a common workflow for analysts who need to quickly filter and analyze large JSON logs. I also encountered a syntax error when attempting to filter by flow ID, which reinforced the importance of correct jq syntax.

Reflection

This lab strengthened my understanding of intrusion detection workflows. I practiced writing custom Suricata rules, running Suricata in offline mode, and analyzing both summary and detailed alert logs. I also used jq to parse JSON logs, which is an essential skill for working with modern security tools. This hands-on experience demonstrates my ability to interpret IDS alerts and understand how network traffic triggers detection rules.
