Lab 2 – Applying OS Hardening Techniques

Course 3 - Connect and Protect: Networks and Network Security

Overview

In this lab, I investigated a security incident affecting the website yummyrecipesforme.com. Using a tcpdump traffic log, I analyzed DNS and HTTP activity between a user’s machine and multiple web servers to identify what happened, which network protocols were involved, and how the user was redirected to a potentially malicious site. I then documented the incident in a structured security report and recommended a mitigation to reduce the risk of similar attacks in the future.

Tools Used

  • tcpdump network traffic log
  • DNS and HTTP protocol analysis
  • Linux-style log interpretation (timestamps, flags, ports)
  • Security incident reporting and documentation

What I Learned

  • DNS and HTTP behavior: How DNS queries resolve domain names to IP addresses and how HTTP connections are established over TCP (port 80).
  • Reading tcpdump logs: How to interpret source/destination, ports, flags, and HTTP GET requests to reconstruct what happened during an incident.
  • Detecting malicious redirects: How multiple DNS lookups and changing destination IPs can indicate DNS spoofing or redirection to a spoofed site.
  • Incident documentation: How to clearly describe the protocol used, the sequence of events, and the likely attack behavior in a security incident report.
  • Mitigation thinking: How to propose a concrete remediation (like MFA or other controls) to reduce the impact of similar attacks.

Scenario

As a cybersecurity analyst for yummyrecipesforme.com, I was notified that visitors were experiencing a security issue when loading the main webpage. My task was to review captured network traffic, identify which protocols were involved, determine what occurred during the incident, and recommend a security measure to prevent similar problems in the future.

The provided tcpdump log showed DNS queries for yummyrecipesforme.com and later for greatrecipesforme.com, followed by HTTP connections to different IP addresses. This pattern suggested that users might have been redirected away from the legitimate site to another domain that could host malicious content.

My Analysis

First, I identified the network protocols involved in the incident. The log showed DNS queries resolving domain names (e.g., yummyrecipesforme.com and greatrecipesforme.com) and HTTP traffic over port 80. These protocols were central to how the attack unfolded.

The tcpdump entries indicated that the user’s machine performed a normal DNS lookup for yummyrecipesforme.com, which resolved to IP 203.0.113.22. A standard TCP three-way handshake followed, along with an HTTP GET / HTTP/1.1 request to that server. After some time, another DNS query was made for greatrecipesforme.com, which resolved to a different IP (192.0.2.17), and a new HTTP connection was established to that host.

This shift from the legitimate domain to a different domain and IP suggests a malicious redirect, likely due to DNS spoofing or malware manipulating DNS responses. The attacker effectively redirected traffic from the original site to a spoofed domain, where users could be exposed to malicious content or phishing pages.

In the incident report, I documented the protocols involved (DNS and HTTP), the sequence of events, and the evidence of redirection. For remediation, I recommended implementing stronger security controls—such as multi-factor authentication (MFA) and improved DNS security measures—to reduce the impact of credential theft and malicious redirection in future incidents.
